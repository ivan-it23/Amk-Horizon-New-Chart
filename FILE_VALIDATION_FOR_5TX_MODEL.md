# Проверка валидности входных файлов для текущей canonical модели `GP_TOOL_DATA`

## Назначение документа

Этот документ фиксирует **актуальную логику файловой валидации**, реализованную в текущем приложении.

Исторически он основан на стабильной схеме из старого проекта, но описывает только то, что действительно поддерживается сейчас в `DataModule` и `ToolDataAdapterRegistry`.

Текущая canonical storage-модель приложения:

```cpp
struct _5Tx_DATA {
    uint32_t signature;
    uint32_t condition;
    uint32_t frame;
    float temperature;
    float rho_smt[2][5];
    float phase_smt[2][5];
    float AM_RX_1[2][5];
    float ZERO_AM_RX_1[2];
    float AM_RX_2[2][5];
    float ZERO_AM_RX_2[2];
    float DELTA_PH[2][5];
    float ZERO_dPH[2];
};
```

В коде эта структура представлена как `GP_TOOL_DATA` размером **240 байт**.

---

## 1. Что считается поддерживаемым сейчас

На текущем этапе приложение принимает файлы, для которых:

- расширение поддерживается контейнерной логикой (`.bin`, `.biv`, `.dev`)
- сигнатура распознаётся через `ToolDataAdapterRegistry`
- найденный адаптер поддерживает данный контейнер
- размер файла кратен физическому размеру кадра выбранного контейнера

Поддерживаемые коды типа прибора по сигнатуре:

- `AUTONOM_5Tx = 151`
- `AUTONOM_5Tx_SDR = 152`
- `LWD_4Tx = 241`

Что сейчас **не считается поддерживаемым**:

- `CARTOGRAPH = 351`
- любые неизвестные сигнатуры
- файлы, у которых размер или смещения не соответствуют ожидаемому физическому кадру

---

## 2. Что проверяется при открытии файла

При вызове `DataModule::ValidateDataFile(...)` и `DataModule::LoadDataFromFile(...)` выполняются следующие проверки.

### Проверка 1. Файл должен открываться

Если файл не удалось открыть:

```text
Не удалось открыть файл данных
```

### Проверка 2. Расширение должно быть поддерживаемым

Допустимы только:

- `.bin`
- `.biv`
- `.dev` / `.DEV`

Если расширение не входит в этот набор:

```text
Неподдерживаемый формат файла
```

### Проверка 3. Сигнатура должна читаться с правильного смещения

Используются те же базовые правила, что и в legacy-логике:

- `.bin/.biv` → `offset 0`
- `.DEV` → `offset 11`

Если 4 байта сигнатуры прочитать нельзя:

```text
Файл слишком короткий или не содержит корректную сигнатуру
```

### Проверка 4. Сигнатура должна маршрутизироваться в поддерживаемый адаптер

Используется правило:

```text
toolCode = (((signature << 12) >> 12) / 1000)
```

После чтения сигнатуры приложение ищет адаптер через `ToolDataAdapterRegistry::FindAdapterBySignature(...)` и дополнительно проверяет `adapter->SupportsFileFormat(format)`.

Сообщение:

```text
Файл содержит неподдерживаемую структуру данных.
Приложение поддерживает только структуры AUTONOM_5Tx или LWD legacy (240 байт на кадр).
```

### Проверка 5. Размер файла должен быть кратен физическому кадру

После определения формата проверяется кратность размера файла ожидаемому физическому кадру:

- `.bin/.biv` → `240` байт
- `.DEV` → `11 + 240 = 251` байт

Если размер не кратен ожидаемому кадру:

```text
Файл содержит неподдерживаемую структуру данных.
Приложение поддерживает только структуры AUTONOM_5Tx или LWD legacy (240 байт на кадр).
```

## 3. Практический алгоритм текущей валидации

```pseudo
function validateFile(path):
    if file not open:
        return error("Не удалось открыть файл данных")

    ext = lower(extension(path))
    if ext not in [".bin", ".biv", ".dev"]:
        return error("Неподдерживаемый формат файла")

    pre = (ext == ".dev") ? 11 : 0

    if fileSize < pre + 4:
        return error("Файл слишком короткий или не содержит корректную сигнатуру")

    sign = readUInt32AtOffset(pre)
    adapter = findAdapterBySignature(sign)

    if adapter is null or adapter does not support ext:
        return error("Файл содержит неподдерживаемую структуру данных...")

    frameSize = (ext == ".dev") ? 251 : 240
    if fileSize < frameSize or fileSize % frameSize != 0:
        return error("Файл содержит неподдерживаемую структуру данных...")

    return ok
```

## 4. Что документ сознательно не обещает

Этот документ **не утверждает**, что в приложении уже реализованы:

- полная структурная валидация входных данных с COM-порта по аналогии с файлом

При этом он фиксирует, что adapter-driven parsing и canonical materialization для `LWD_4Tx` уже присутствуют в текущем коде.

Для COM-порта в приложении есть собственная логика протокольной проверки в `SerialModule`, но она не должна смешиваться с текущим контрактом файловой валидации.
