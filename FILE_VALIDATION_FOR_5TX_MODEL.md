# Проверка валидности входных данных для модели `_5Tx_DATA`

## Назначение документа

Этот документ описывает, как в старом проекте фактически проверяется валидность входных данных:

- при открытии файла данных
- при получении структуры с COM-порта

Документ адаптирован под новую версию приложения, где внутренняя целевая структура только одна:

```cpp
struct _5Tx_DATA {
    uint32_t signature;
    uint32_t condition;
    uint32_t frame;
    float temperature;
    float rho_smt[2][5];
    float phase_smt[2][5];
    float AM_RX_1[2][5];
    float ZERO_AM_RX_1[2];
    float AM_RX_2[2][5];
    float ZERO_AM_RX_2[2];
    float DELTA_PH[2][5];
    float ZERO_dPH[2];
};
```

Главное правило новой версии:

- если входные данные можно интерпретировать как `_5Tx_DATA` напрямую или привести к `_5Tx_DATA`, то данные поддерживаются
- если входные данные нельзя интерпретировать или привести к `_5Tx_DATA`, должно выводиться сообщение:

```text
Неподдерживаемая структура данных
```

или

```text
Файл содержит неподдерживаемую структуру данных
```

---

## Какие типы входных данных считаются поддерживаемыми

Для новой версии в терминах старого проекта поддерживаются только:

- `AUTONOM_5Tx = 151`
- `AUTONOM_5Tx_SDR = 152`
- `LWD_4Tx = 241`

При этом:

- `AUTONOM_5Tx` и `AUTONOM_5Tx_SDR` поддерживаются напрямую через `_5Tx_DATA`
- `LWD_4Tx` поддерживается через чтение `_4Tx_DATA` и преобразование в `_5Tx_DATA`

Неподдерживаемым для новой версии следует считать:

- `CARTOGRAPH = 351`
- любые неизвестные сигнатуры
- любые пакеты/файлы с некорректной длиной, CRC или смещением, если из них нельзя достоверно извлечь поддерживаемую структуру

---

## Где в старом проекте находится логика проверки

Основные места:

- `MyForm.h`
  - `data_Click(...)` — открытие файла
  - `toolStripButton_on_off_Click(...)` — подключение к прибору и определение типа
  - `timer_get_data_from_sonde(...)` — чтение кадров с COM-порта
- `variable.cpp`
  - `define_sonde_type(DATA_FILE_PARAM *param)` — определение типа прибора по сигнатуре файла
  - `get_sonde_id(uint32_t signature)` — декодирование сигнатуры
  - `receive_from_tool(...)` — валидация пакета, CRC и длины ответа с COM-порта
  - `read_blok(...)` — чтение кадра из файла

# 1. Валидация файла данных

## Что делает старый проект

При открытии файла старая программа не делает одной отдельной функции `validateFile(...)`, но фактически валидирует файл через такую последовательность:

1. пытается открыть файл
2. определяет расширение
3. читает сигнатуру с правильного смещения
4. определяет тип прибора по сигнатуре
5. вычисляет число кадров
6. пытается читать кадры функцией `read_blok(...)`

Если эта цепочка отрабатывает корректно, файл считается пригодным к дальнейшей обработке.

## Проверка 1. Файл должен открываться

Старый код при открытии сначала проверяет, что файл реально существует и доступен для чтения.

Для новой версии это первое обязательное условие валидности.

Если файл не открылся:

```text
Не удалось открыть файл данных
```

## Проверка 2. Расширение должно быть поддерживаемым

В старом проекте в фильтре открытия поддерживаются:

- `.bin`
- `.biv`
- `.DEV`
- также есть другие расширения, но они не относятся к рассматриваемой бинарной структуре

Для новой версии, если речь именно о чтении структуры данных прибора, разумно считать поддерживаемыми:

- `.bin`
- `.biv`
- `.dev` / `.DEV`

Если расширение не поддерживается:

```text
Неподдерживаемый формат файла
```

## Проверка 3. Нужно корректно прочитать сигнатуру

Старый код использует разное смещение для сигнатуры:

- `.bin` / `.biv` → сигнатура в байтах `0..3`
- `.DEV` → сигнатура в байтах `11..14`

Если файл слишком короткий и 4 байта сигнатуры прочитать нельзя, файл нужно считать невалидным.

Сообщение:

```text
Файл слишком короткий или не содержит корректную сигнатуру
```

## Проверка 4. Нужно корректно декодировать тип прибора

Старый код извлекает тип так:

```text
buff = signature << 12
buff = buff >> 12
toolCode = buff / 1000
```

Логика `get_sonde_id(...)` дополнительно разбирает сигнатуру на поля:

- `type_ = buff / 100000`
- `N_Tx = (buff % 100000) / 10000`
- `mod = (buff % 10000) / 1000`
- `number = buff % 1000`
- `type = buff / 1000`

Для новой версии валидными считаются только:

- `241`
- `151`
- `152`

Если тип другой:

```text
Файл содержит неподдерживаемую структуру данных
```

Это ключевая проверка на уровне структуры.

## Проверка 5. Структура кадра должна соответствовать поддерживаемому типу

После определения типа нужно убедиться, что файл можно читать ожидаемыми блоками.

### Для `AUTONOM_5Tx` / `AUTONOM_5Tx_SDR`

Поддерживаемые блоки:

- `.bin/.biv` → `_5Tx_DATA`
- `.DEV` → `11 байт служебных + _5Tx_DATA`

То есть файл валиден, если его можно разбить на такие кадры.

### Для `LWD_4Tx`

Поддерживаемые блоки:

- `.bin/.biv` → `_4Tx_DATA`
- `.DEV` → `11 байт служебных + _4Tx_DATA`

Такой файл считается поддерживаемым, потому что `_4Tx_DATA` можно привести к `_5Tx_DATA` через адаптер.

### Для `CARTOGRAPH`

Даже если старый проект умеет читать такие данные, для новой версии этот тип нужно считать неподдерживаемым, если приложение целенаправленно работает только через `_5Tx_DATA` для `Автономный` и `LWD`.

Сообщение:

```text
Файл содержит неподдерживаемую структуру данных
```

## Проверка 6. Размер файла должен быть кратен размеру физического кадра

Это правило прямо не оформлено одной строкой в старом UI-коде, но логически следует из `define_sonde_type(...)` и `read_blok(...)`.

Для новой версии рекомендуется считать файл валидным только если после определения типа прибора выполняется одно из правил:

### `AUTONOM_5Tx` / `AUTONOM_5Tx_SDR`

- `.bin/.biv`
  - `fileSize % sizeof(_5Tx_DATA) == 0`
- `.DEV`
  - `fileSize % (11 + sizeof(_5Tx_DATA)) == 0`

### `LWD_4Tx`

- `.bin/.biv`
  - `fileSize % sizeof(_4Tx_DATA) == 0`
- `.DEV`
  - `fileSize % (11 + sizeof(_4Tx_DATA)) == 0`

Если это не выполняется:

```text
Файл имеет некорректную длину для ожидаемой структуры данных
```

Это особенно полезно в новой версии, потому что делает валидацию явной, а не неявной через неудачное чтение.

# 2. Валидация данных с COM-порта

## Что делает старый проект

Для COM-порта старая версия выполняет более явную валидацию, чем для файлов.

Валидация фактически состоит из трёх уровней:

- проверка, что вообще пришёл ответ
- проверка длины и CRC пакета
- проверка, что полезная нагрузка соответствует ожидаемому типу прибора

## Проверка 1. Устройство должно ответить

В `receive_from_tool(...)` сначала читаются первые 3 байта заголовка пакета.

Если чтение не удалось:

- ответ считается невалидным
- функция возвращает ошибку

Для новой версии это означает:

```text
Нет ответа от прибора
```

## Проверка 2. Пакет должен иметь корректную длину

Старый код читает длину из заголовка и вычисляет оставшуюся длину пакета:

```text
rest_length_for_read = packetLength - 3
```

Потом дочитывает остаток пакета.

Если пакет дочитан не полностью, данные невалидны.

Сообщение:

```text
Получен неполный пакет данных
```

## Проверка 3. CRC пакета должна быть корректной

`receive_from_tool(...)` проверяет:

- CRC по содержимому пакета
- совпадение длины реально прочитанных данных с ожидаемой

Если CRC не совпала или пакет прочитан не полностью, функция возвращает ошибку.

Для новой версии это обязательная проверка валидности.

Сообщение:

```text
Получен повреждённый пакет данных
```

или

```text
CRC пакета невалидна
```

## Проверка 4. Полезная нагрузка должна иметь ожидаемую длину

В старом проекте это видно особенно явно на `CARTOGRAPH`, где проверяется `income_length == sizeof(DATA)` или `sizeof(DATA) + sizeof(RAW_DATA)`.

Для `LWD` и `AUTONOM` в явном виде это проверяется слабее, но фактическая логика всё равно опирается на ожидаемый размер структуры.

Для новой версии следует сделать эту проверку строгой:

### Если ожидается `AUTONOM_5Tx`

Полезная нагрузка должна иметь размер:

```text
sizeof(_5Tx_DATA)
```

### Если ожидается `LWD_4Tx`

Полезная нагрузка должна иметь размер:

```text
sizeof(_4Tx_DATA)
```

Если длина другая:

```text
Получена неподдерживаемая структура данных
```

## Проверка 5. Сигнатура структуры должна соответствовать поддерживаемому типу

Это главная смысловая проверка.

### При подключении к прибору

Старый код посылает команду чтения сигнатуры и затем проверяет её через `get_sonde_id(signature)`.

Если сигнатуру получить не удалось, старая программа делает fallback:

```text
ID НЕ ПОЛУЧЕН, БУДЕТ УСТАНАВЛЕН ТИП LWD_4Tx!
```

Для новой версии такой fallback лучше не переносить как есть, если тебе нужна строгая валидация.

Безопаснее правило:

- если сигнатура не получена, данные считаются неподтверждёнными
- пока тип не определён, поток данных нельзя считать валидным

Сообщение:

```text
Не удалось определить тип прибора по сигнатуре
```

### При получении самого кадра данных

Старая программа делает:

- для `AUTONOM`
  - читает `_5Tx_DATA`
  - берёт `signature` из структуры
  - вызывает `get_sonde_id(...)`
  - принимает кадр только если тип `151` или `152`
- для `LWD`
  - читает `_4Tx_DATA`
  - берёт `signature` из структуры
  - вычисляет `signature_for_pallete`
  - принимает кадр только если тип `241`

Для новой версии это означает:

- даже если пакет пришёл и имеет корректную длину, он всё равно невалиден, если сигнатура структуры не соответствует поддерживаемому типу

Если тип не один из `241`, `151`, `152`:

```text
Получена неподдерживаемая структура данных
```

# 3. Что считать валидным в новой версии

## Валидный файл

Файл следует считать валидным только если одновременно выполняется всё ниже:

- файл открылся
- расширение поддерживается
- сигнатура прочиталась с правильного смещения
- тип прибора по сигнатуре один из `241`, `151`, `152`
- размер файла кратен размеру ожидаемого физического кадра
- кадры можно прочитать без выхода за границы файла
- данные либо уже `_5Tx_DATA`, либо могут быть преобразованы из `_4Tx_DATA` в `_5Tx_DATA`

## Валидный пакет с COM-порта

Пакет следует считать валидным только если одновременно выполняется всё ниже:

- устройство ответило
- заголовок пакета прочитан
- полная длина пакета совпадает с ожидаемой
- CRC корректна
- полезная нагрузка имеет ожидаемый размер структуры
- сигнатура в структуре соответствует `241`, `151` или `152`
- структура либо уже `_5Tx_DATA`, либо приводима из `_4Tx_DATA` к `_5Tx_DATA`

# 4. Что считать неподдерживаемой структурой данных

В новой версии вход нужно считать неподдерживаемым в любом из случаев:

- сигнатура не читается
- сигнатура декодируется в неизвестный тип прибора
- тип прибора равен `CARTOGRAPH` или другому неподдерживаемому семейству
- размер полезной структуры не совпадает ни с `_5Tx_DATA`, ни с `_4Tx_DATA`
- для `.DEV` не соблюдается требуемое смещение/размер физического блока
- пакет COM-порта не проходит CRC
- пакет COM-порта имеет некорректную длину
- `LWD_4Tx` не удаётся преобразовать в `_5Tx_DATA`

Рекомендуемое унифицированное сообщение:

```text
Неподдерживаемая структура данных
```

Альтернативные, более точные сообщения:

- `Файл содержит неподдерживаемую структуру данных`
- `Получена неподдерживаемая структура данных с COM-порта`
- `Не удалось определить тип прибора по сигнатуре`
- `Структура данных не соответствует ожидаемому формату`

# 5. Рекомендуемая логика проверки в новой версии

## Проверка файла

```pseudo
function validateFile(path):
    if file not open:
        return error("Не удалось открыть файл данных")

    ext = lower(extension(path))
    if ext not in [".bin", ".biv", ".dev"]:
        return error("Неподдерживаемый формат файла")

    pre = (ext == ".dev") ? 11 : 0

    if fileSize < pre + 4:
        return error("Файл слишком короткий или не содержит корректную сигнатуру")

    sign = readUInt32AtOffset(pre)
    toolCode = (((sign << 12) >> 12) / 1000)

    if toolCode not in [241, 151, 152]:
        return error("Файл содержит неподдерживаемую структуру данных")

    if toolCode in [151, 152]:
        frameSize = (ext == ".dev") ? 11 + sizeof(_5Tx_DATA) : sizeof(_5Tx_DATA)
        direct5Tx = true
    else if toolCode == 241:
        frameSize = (ext == ".dev") ? 11 + sizeof(_4Tx_DATA) : sizeof(_4Tx_DATA)
        direct5Tx = false

    if fileSize % frameSize != 0:
        return error("Файл имеет некорректную длину для ожидаемой структуры данных")

    return ok(toolCode, direct5Tx)
```

## Проверка пакета с COM-порта

```pseudo
function validateComPayload(packet):
    if no response:
        return error("Нет ответа от прибора")

    if packet length invalid:
        return error("Получен неполный пакет данных")

    if crc invalid:
        return error("CRC пакета невалидна")

    sign = extractSignatureFromPayload(packet)
    toolCode = (((sign << 12) >> 12) / 1000)

    if toolCode == 241:
        expectedSize = sizeof(_4Tx_DATA)
    else if toolCode in [151, 152]:
        expectedSize = sizeof(_5Tx_DATA)
    else:
        return error("Получена неподдерживаемая структура данных")

    if payloadSize != expectedSize:
        return error("Получена неподдерживаемая структура данных")

    return ok(toolCode)
```

# 6. Практический итог

## Что реально нужно перенести из старого проекта

Из старого проекта в новую версию нужно перенести не UI-ветки, а сами правила валидности:

- чтение сигнатуры с правильного смещения
- нормализацию сигнатуры
- декодирование типа прибора
- проверку длины файла/пакета
- проверку CRC для COM-порта
- проверку, что структура относится к `AUTONOM_5Tx`, `AUTONOM_5Tx_SDR` или `LWD_4Tx`
- правило, что `LWD_4Tx` допустим только если есть адаптер в `_5Tx_DATA`

## Какое правило должно быть главным в новой версии

Главное правило такое:

- **валидны только данные, которые можно представить в модели `_5Tx_DATA`**

То есть:

- `AUTONOM_5Tx` → валиден напрямую
- `AUTONOM_5Tx_SDR` → валиден напрямую
- `LWD_4Tx` → валиден только как поддерживаемый источник для адаптации в `_5Tx_DATA`
- всё остальное → неподдерживаемая структура данных

## Рекомендуемое итоговое сообщение об ошибке

Если тебе нужно одно общее сообщение для UI, лучше использовать:

```text
Неподдерживаемая структура данных
```

Если нужны более точные причины, лучше показывать их до этого общего статуса:

- ошибка открытия файла
- неподдерживаемое расширение
- сигнатура не прочитана
- неизвестный тип прибора
- неверная длина кадра
- CRC невалидна
- структура не приводится к `_5Tx_DATA`
