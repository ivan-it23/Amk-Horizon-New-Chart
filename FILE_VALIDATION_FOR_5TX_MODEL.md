# Валидация входных файлов

> Имя файла историческое, но содержание относится ко **всем текущим поддерживаемым моделям**, а не только к `5Tx`.

## Назначение документа

Этот документ описывает **реальную текущую** логику проверки файла перед загрузкой.

Источники истины:

- `Amk-Horizon-New-Chart/DataModule.cpp`
- `Amk-Horizon-New-Chart/ToolDataAdapters.h/.cpp`
- `Amk-Horizon-New-Chart/ToolDataTypes.h`

## 1. Когда файл считается поддерживаемым

Файл считается валидным для открытия, если одновременно выполняются условия:

1. расширение поддерживается;
2. `signature` читается с корректного смещения;
3. по `signature` найден адаптер;
4. адаптер поддерживает данный контейнер;
5. размер файла кратен физическому размеру кадра.

Эта валидация отвечает на вопрос:

- **можно ли загрузить файл в текущий pipeline**

Она **не отвечает** на вопрос:

- физически корректны ли все численные поля каждого кадра.

## 2. Допустимые расширения

Поддерживаются только:

- `.bin`
- `.biv`
- `.DEV`

Другие расширения отклоняются сразу.

## 3. Физический размер кадра

- `.bin` -> `240`
- `.biv` -> `240`
- `.DEV` -> `251`

Для `.DEV`:

`251 = 11 bytes header + 240 bytes payload`

Проверка кратности идёт по **physical frame size**, а не просто по `sizeof(GP_TOOL_DATA)`.

## 4. Как читается `signature`

### `.bin` / `.biv`

Сигнатура читается с начала первого кадра.

### `.DEV`

Сигнатура читается после пропуска первых `11` байт заголовка.

## 5. Поддерживаемые сигнатуры

Сейчас допустимы:

- `151` -> `AUTONOM_5TX`
- `152` -> `AUTONOM_5TX_SDR`
- `241` -> `LWD_4TX`

Если адаптер по сигнатуре не найден, файл отклоняется.

## 6. Что делает адаптер на этапе проверки

После чтения сигнатуры код:

- находит адаптер в `ToolDataAdapterRegistry`;
- спрашивает у адаптера, допустим ли данный контейнер;
- только после этого считает файл пригодным для чтения.

То есть реальная логика проверки:

`extension + signature + adapter + container support + file size multiplicity`

## 7. Что происходит после успешной проверки

После успешной валидации:

1. файл читается по физическим кадрам;
2. каждый кадр идёт в `ParseRawFrameDetailed(...)`;
3. получается `ParsedToolFrame`;
4. данные materialize-ятся в:
   - `GP_TOOL_DATA`
   - `ToolRecordMetadata`

## 8. Особенность `LWD_4TX`

Для `241` нужно разделять две стадии:

- **валидация файла**
- **интерпретация конкретного 240-байтного кадра**

Текущая валидация:

- не различает подробно legacy/canonical layout внутри `LWD_4TX`;
- только подтверждает, что контейнер и сигнатура поддерживаются.

А уже `ParseRawFrameDetailed(...)` решает:

- это legacy raw `LEGACY_GP_TOOL_DATA`;
- или canonical `GP_TOOL_DATA`;
- нужен ли путь через `Lwd4TxAdapter`.

## 9. Что текущая валидация не обещает

Текущая логика **не обещает**:

- восстановление повреждённого файла;
- подбор альтернативного смещения;
- глубокую физическую верификацию каждого значения;
- хранение исходного raw layout после загрузки;
- adapter-aware export policy.

## 10. Псевдокод текущего алгоритма

```text
detect extension
if extension not supported -> reject

read signature from proper offset
find adapter by signature
if adapter not found -> reject

check adapter supports current container
if not supported -> reject

get physical frame size
if file size == 0 or not divisible by frame size -> reject

accept file for parsing
```

## 11. Практический итог

Файл поддерживается не потому, что это “какой-то 240-байтный бинарник”, а потому что:

- расширение допустимо;
- сигнатура распознаётся;
- адаптер найден;
- контейнер поддерживается;
- размер кратен physical frame size.

Только после этого начинается реальный parsing path.
