# Анализ форматов файлов данных: `.bin`, `.biv`, `.DEV`

> Статус: актуально для текущей реализации `DataModule`.

## Назначение документа

Этот документ фиксирует **текущую, реализованную** логику чтения файлов данных в приложении.

Он не описывает все legacy-варианты и не пытается документировать неподдержанные структуры. Для исторических деталей см. `FILE_FORMATS_BIN_BIV_DEV_FOR_5TX_MODEL.md`.

---

## 1. Поддерживаемая структура данных

Во всех поддерживаемых файловых контейнерах приложение читает полезную нагрузку через adapter-driven parsing и затем материализует её в canonical shape:

```cpp
struct GP_TOOL_DATA {
    uint32_t signature;
    uint32_t condition;
    uint32_t frame;
    float temperature;
    float rho_smt[2][5];
    float phase_smt[2][5];
    float AM_RX_1[2][5];
    float ZERO_AM_RX_1[2];
    float AM_RX_2[2][5];
    float ZERO_AM_RX_2[2];
    float DELTA_PH[2][5];
    float ZERO_dPH[2];
};
```

- Размер структуры: **240 байт**
- Внутренняя canonical storage/API модель приложения: **`GP_TOOL_DATA`**
- Adapter-level parsing route: **`ToolDataAdapterRegistry -> ParsedToolFrame -> GP_TOOL_DATA + ToolRecordMetadata`**
- Текущая поддержка по сигнатуре: **`151`**, **`152`**, **`241`**

---

## 2. Поддерживаемые контейнеры

| Формат | Физическая организация | Размер физического кадра |
|--------|-------------------------|---------------------------|
| `.bin` | последовательность `GP_TOOL_DATA` | `240` байт |
| `.biv` | идентичен `.bin` | `240` байт |
| `.DEV` | `11` байт служебных + `GP_TOOL_DATA` | `251` байт |

### Практические правила

- `.biv` читается **тем же reader**, что и `.bin`
- `.DEV` читается с пропуском **11 байт** перед каждым полезным кадром
- содержимое 11-байтного префикса `.DEV` сейчас **не интерпретируется**

---

## 3. Смещения и чтение кадров

### `.bin` / `.biv`

```text
offset = n * 240
read 240 bytes as GP_TOOL_DATA
```

### `.DEV`

```text
blockOffset = n * 251
skip 11 bytes
read 240 bytes as GP_TOOL_DATA
```

---

## 4. Что проверяется до чтения

Перед загрузкой файл проходит валидацию:

- расширение должно быть одним из `.bin`, `.biv`, `.dev`
- сигнатура должна читаться с корректного смещения:
  - `.bin/.biv` → `offset 0`
  - `.DEV` → `offset 11`
- тип прибора декодируется по правилу:

```text
toolCode = (((signature << 12) >> 12) / 1000)
```

- сигнатура должна соответствовать адаптеру, который поддерживает данный контейнер
- размер файла должен быть кратен физическому размеру кадра выбранного контейнера

Подробная логика — в `FILE_VALIDATION_FOR_5TX_MODEL.md`.

---

## 5. Что важно про текущие ограничения

Хотя `LWD_4Tx (241)` теперь поддерживается на уровне adapter parsing и файловой валидации, это не означает полного исчезновения legacy-границ:

- после чтения данные всё ещё материализуются в canonical `GP_TOOL_DATA`
- часть верхней UI/SMT-логики по-прежнему сохраняет 5Tx-centric contract
- canonical `.bin` export остаётся текущим compatibility persistence path

Это важно: документ описывает именно **текущее поведение приложения**, а не целевую будущую архитектуру после полного удаления compatibility shortcut-ов.
