# Анализ форматов файлов данных (`.bin`, `.biv`, `.DEV`)

## Назначение документа

Этот файл описывает **текущую реализованную в коде файловую модель**, а не исторические варианты.

Если есть расхождение, источником истины считаются:

- `Amk-Horizon-New-Chart/DataModule.cpp`
- `Amk-Horizon-New-Chart/ToolDataAdapters.h/.cpp`
- `Amk-Horizon-New-Chart/ToolDataTypes.h`

## 1. Текущий файловый контракт

При открытии файла приложение работает так:

1. определяет контейнер по расширению;
2. читает `signature` с корректного смещения;
3. находит адаптер через `ToolDataAdapterRegistry`;
4. проверяет, поддерживает ли адаптер этот контейнер;
5. проверяет кратность размера физическому кадру;
6. читает все кадры;
7. прогоняет каждый кадр через `ParseRawFrameDetailed(...)`;
8. сохраняет результат как canonical `GP_TOOL_DATA` + `ToolRecordMetadata`.

Ключевая идея:

- контейнер и внутренняя data-модель — не одно и то же;
- после загрузки приложение уже работает **не с raw layout**, а с canonical shape.

## 2. Поддерживаемые контейнеры

### `.bin`

- последовательность физических кадров по `240` байт;
- без служебного заголовка на кадр.

### `.biv`

- обрабатывается так же, как `.bin`;
- физический размер кадра также `240` байт.

### `.DEV`

- на каждый кадр есть `11` служебных байт заголовка;
- затем идёт `240` байт полезной нагрузки;
- физический размер кадра: `251` байт.

## 3. Поддерживаемые сигнатуры

На текущем этапе поддерживаются:

- `151` -> `AUTONOM_5TX`
- `152` -> `AUTONOM_5TX_SDR`
- `241` -> `LWD_4TX`

## 4. Adapter-driven выбор структуры

Файл выбирает не “одну общую бинарную структуру”, а adapter path:

- сигнатура определяет `ToolDataKind`;
- адаптер определяет `ToolCapabilities`;
- адаптер знает, какие контейнеры допустимы;
- адаптер отвечает за преобразование raw frame в canonical shape.

Практически это значит:

- расширение файла само по себе недостаточно;
- одинаковый размер payload (`240`) ещё не означает одинаковый raw layout;
- особенно это важно для `LWD_4TX`.

## 5. Canonical размер и physical frame size

Текущие стабильные размеры:

```cpp
sizeof(GP_TOOL_DATA) == 240
sizeof(METROLOGY_DATA) == 240
```

Физический шаг чтения:

- `.bin/.biv` -> `240`
- `.DEV` -> `251`

Важно:

- `240` байт canonical shape **не означает**, что любой входной `240`-байтный кадр уже совпадает с внутренней моделью;
- raw frame может быть преобразован адаптером перед сохранением в `GP_TOOL_DATA`.

## 6. Реальная логика чтения по контейнерам

### 6.1 `.bin` / `.biv`

- сигнатура читается из начала первого кадра;
- файл валиден, если его размер кратен `240`;
- кадры читаются по `240` байт;
- каждый кадр проходит через `ParseRawFrameDetailed(...)`.

### 6.2 `.DEV`

- сигнатура читается после первых `11` байт заголовка;
- файл валиден, если его размер кратен `251`;
- для каждого кадра:
  - пропускаются `11` байт;
  - читаются `240` байт payload;
  - payload подаётся в adapter parsing path.

## 7. `LWD_4TX` как special case

Для `241` сейчас поддерживаются **два разных 240-байтных варианта**:

- legacy raw `LEGACY_GP_TOOL_DATA`;
- canonical `GP_TOOL_DATA`.

### 7.1 Что делает код

`DataModule::ParseRawFrameDetailed(...)` для `LWD_4TX`:

- проверяет, не выглядят ли canonical `T5`-слоты как legacy-мусор;
- дополнительно сравнивает plausibility по `frame` и `temperature`;
- при необходимости отправляет кадр в `Lwd4TxAdapter::ParseRawFrame(...)`;
- иначе допускает canonical passthrough.

### 7.2 Почему это важно

Это нужно, чтобы одновременно поддерживать:

- старые `4Tx` файлы;
- уже сохранённые canonical `4Tx` файлы;
- обычные `5Tx` данные.

## 8. Что получается после чтения

После успешной загрузки приложение хранит:

- `GP_TOOL_DATA`
- `ToolRecordMetadata`

Дальше верхний слой работает через:

- `ToolDataAccessView`
- `MeasurementView`

Именно поэтому file-loading документация должна говорить не только о формате кадра, но и о **capabilities**, которые дошли до UI.

## 9. Что текущая файловая модель не обещает

Текущая реализация **не обещает**:

- восстановление произвольно повреждённых файлов;
- “умный” подбор смещения без валидной сигнатуры;
- сохранение исходного raw container/layout после загрузки;
- adapter-aware export policy;
- одинаковое runtime поведение для `4Tx` и `5Tx` без учёта metadata.

## 10. Практический итог

Текущая модель чтения такая:

- `.bin` и `.biv` — контейнеры с шагом `240`;
- `.DEV` — контейнер с шагом `251`;
- структура выбирается по `signature` и адаптеру;
- `LWD_4TX` требует различать legacy raw и canonical `240`-байтный кадр;
- после чтения всё materialize-ится в canonical `GP_TOOL_DATA` и сопровождается `ToolRecordMetadata`.
